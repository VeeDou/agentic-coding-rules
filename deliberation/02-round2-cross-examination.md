## 一、Claude Code 正面回应 Codex 的 5 个挑战

### 1. 一个两边都会出错的例子，以及怎么判定最小实现（回应反例挑战）

场景：业务里已经接了一家大模型服务商，现在要接第二家。
- **过度抽象：** 新建 `ProviderAdapter` 接口，加工厂函数和 `providers.yaml`。现在只有两家，就搭起了三层结构。
- **特化硬编码：** 在业务函数里写 `if provider == "xxx":`，往后每接一家，这里就多一个分支。

现有规则两边都能被引用：Rule of Three 说“还没到第三处，别抽象”；防特化说“别写死分支”。所以 agent 选哪边都能找到依据。

要的不是更多口号，而是一条判定规则：**差异是值，就放进数据；差异是行为，就先并列写两份，到第三处才抽象。**
- 如果两家的区别只是 base URL、请求头、模型名，那就是值：一个调用函数加一份服务商配置记录，不需要接口，也不需要分支。
- 如果流式协议不一样，那是行为：并列写两个函数，到第三家出现时再抽出共性。

这条规则对任何输入都能给出唯一答案，而且不引入新概念。

### 2. 自己写代码又自己填清单，怎么防止给多余的抽象编理由（回应检查点可靠性）

先分清两种失败。“漏报”可以用 Codex 的办法解决：从 `git diff` 机械提取清单，让新增的东西没法漏掉。“编理由”要靠收紧“什么算理由”：
- **理由必须指向一样现在就存在的东西：** 用户的原话、一个已有的调用方、一个失败过的测试、一次实测数据。
- **“隐含的性能或可用性要求”不能当理由。** 既然是隐含的，它本质上就是一条假设。这一项要从“理由”栏挪到“替你做的决定”清单里，交给用户回答是或否。这样编理由的空间就被转成了向用户提出的问题，擅自加的缓存层就是这样被拦下来的。

独立评审什么时候有用，什么时候没用：
- **有用的情况：** 实现方误读了需求，或者 diff 里能看到具体行为问题（事务顺序、默认值被翻转）。评审方没有实现方的思路惯性，也没有“已经写了不舍得删”的心理。
- **基本没用的情况：**
  - 需求本身就模糊：两个模型的训练分布相近，很可能补上同一个默认值。这只有用户能解决。
  - 评审方拿到了实现方的总结：等于在复读同一个偏差。
  - 评审问题是“这样可以吗”：模型倾向于附和。问“哪段可以删”才是对抗性的问法。

### 3. 两个具体场景要不要独立评审（回应触发阈值）

- **涉及权限、只改一行：** 要。按后果触发，不看改动大小。而且 diff 只有一行，评审本来就便宜。
- **500 行纯机械迁移：**
  - 如果是确定性工具生成的（codemod、IDE 重命名），并且编译和测试都通过：不评审这 500 行输出，改成评审生成规则或脚本本身。
  - 如果是大模型“手工”完成的：那就算不上机械迁移，至少要抽查，并核对 diff 里是否真的只有标识符变化。
  - 如果迁移涉及数据（比如数据库迁移）：属于不可逆操作，直接触发评审。

### 4. Rule of Three 要不要例外（回应例外机制）

要，但三种例外共用一条证据规则：**例外必须指向现在已经存在的东西。**
- **项目里已有稳定的抽象：** 直接复用，这本来就不算新建抽象。
- **重复已经造成过真实缺陷：** 指出两份代码分叉的那次提交、issue 或测试。
- **安全或性能需要提前设计：** 给出实测数字，或者说明它守的是哪个真实边界上的哪种已知威胁。

“以后可能需要”指向的是不存在的东西，所以自动不成立，不必另写一条禁令。

### 5. 不硬凑条数，先观察效果再加钩子（回应验证实验）

两点都同意。我撤回“≤5 条”的数量限制，改成：**有则如实列，无则不写；多到列不完，说明应该先问用户。**

## 二、Codex 正面回应 Claude Code 的 5 个问题

### 1. 自述遗漏 vs 机械提取

不能保证我能凭记忆列全长任务中新加的内容。应先查看实际工作区状态和 diff，再判断复杂度；但 `git diff` 也有盲区：默认不展示未跟踪文件的内容，且工作区可能混有用户原有改动。因此应结合 `git status`、暂存和未暂存 diff，以及必要时读取未跟踪文件，识别**本次改动**；非 Git 项目则比较适当的变更记录。

“机械盘点”只能帮助发现候选，不能可靠地自动判断哪些是新概念，也不必向用户逐项输出所有普通函数和分支。重点审查有实质设计意义的新增内容，保留证据可追溯即可。

### 2. 对抗评审的信息裁剪

独立上下文有助于减少被实现过程锚定，但“只能看需求、接口和 diff”过窄：评审者可能需要读相关调用方、已有测试、项目规则和运行结果，才能判断兼容性与真实风险。

建议**先不给实现者的结论和会话过程**，让评审者独立形成初判；之后可以按需查看实现者列出的取舍，检查是否存在合理解释或遗漏。不要把信息隔离变成阻止获取证据。

### 3. “只列不补”的边界校准

模型可能倾向于顺手补齐，但“补不补由用户或风险等级决定”如果被解释为**发现必要验证后必须等用户逐项批准**，会削弱已授权的完成义务。

建议区分：
- 为完成本次需求和适当验证而必要的测试或修复：在已授权范围内继续完成。
- 假想风险引出的额外防御、无实际价值的测试或无关改动：不擅自增加；有影响决策的未验证项则如实报告。
- 无法验证、存在重大需求分歧或需要额外授权时：明确说明并寻求所需决定。

因此，原则应叫**“如实报告未验证项，不为清单凑测试”**。

### 4. 不固定角色 + 对抗三问

赞成不固定实现者和评审者，也赞成三问作为审查提示；但三问不应成为每次都必须各找出一项的问题清单。更合适的问法是：
1. 哪些关键假设最可能有误？证据是什么？
2. 现有验证会漏掉哪些有代表性的真实错误？
3. 哪些新增代码、配置或抽象缺少当前需求支持，可以直接删掉？

审查者可以回答“未发现”，但要说明看过什么以及判断的局限。

### 5. 对条文草案的三处反向漏洞拦截

Codex 特别指出了初版合并稿中的三处潜在副作用：
- **“出现不可能值直接报错”不应导致到处加检查：** 内部契约由类型系统、既有断言或调用关系保证；不应为了遵守这句话到处新增冗余运行时校验。应写明“不写静默吞错的兜底分支，也不为‘不可能值’到处新增冗余运行时校验”。
- **测试判据不过度狭隘化：** 测试除了逻辑取反，也可能验证契约、性能或集成行为，重点是“能发现有意义的真实错误，不写改错核心逻辑也不会失败的形式主义测试”。
