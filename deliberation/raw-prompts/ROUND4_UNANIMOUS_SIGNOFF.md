## 二、最终定稿条文（拟替换 `~/agent-config/AGENTS.md` 中“实现的分量”章节）

```markdown
## 实现的分量（防过度设计，也防特化硬编码）

**核心**：通用性做在原语层，特化放在数据层，中间不加抽象层。两者冲突时，选概念更少的方案。通用化应该让机制变少，而不是变多。

**判据**：
- 差异是值（地址、格式、文案、阈值、模型名），用代码内的数据（表或记录）表达，不为假想需求新增配置项；差异是行为（协议、状态流转），先并列写，出现第三次才抽象（Rule of Three）。不为某个具体样例、测试或某一种用户习惯写死分支。
- 面向用户或 agent 的接口从一开始就接受多样输入；能交给模型判断的流程，不硬编码成固定步骤。
- 只做本次明确要求的事；顺手发现的问题列出来，不擅自改。每一行改动都应能追溯到需求；代码量明显超出需求直觉时，先停下说明原因。
- 提前抽象或新增配置项、扩展点、缓存、兼容垫片、兜底分支，必须指向现在已存在的事物（用户原话、已有稳定抽象、已发生缺陷、实测数据、已知外部约束），并说明依据。“以后可能需要”或自行脑补的“隐含要求”不算理由。
- 只在真实边界做错误处理（用户输入、网络、外部 API、持久化存储、并发写入）；内部调用相信调用方与既有契约，不写静默吞错的兜底分支，也不为“不可能值”到处新增冗余运行时校验。

**非琐碎改动（新建文件，新增对外接口、配置项或依赖，或跨模块修改）执行规程**：
1. **动手前**：先读目标代码、必要的调用方和现有测试（无调用方或测试时据实说明）；未搜索项目已有实现前，不新建通用 helper、工具类或模块。按任务风险明确预期行为与验证方式。对影响结果的默认值、范围取舍或需求冲突，如实说明所作判断（不存在时不硬凑）；涉及高后果、重大需求分歧或超出既有授权时，先询问用户。
2. **交付前核对变更**：先给客观证据（实际运行的命令与关键输出），后给结论总结。结合 `git status`、diff 及新增未跟踪文件（非 Git 项目对比相应变更记录），区分本次改动与工作区原有改动；审视有实质设计意义的新增文件、公开接口、类/函数、配置项、兼容逻辑、兜底分支和依赖，确认对应当前需求或已知约束，无法说明必要性的删除或改为文字建议。
3. **验证与未验证范围**：测试应针对真实需求、契约、业务不变量或已知风险，并能发现有意义的错误；不写改错核心逻辑也不会失败的形式主义测试。完成当前需求所需的必要验证与修复应正常执行；交付时如实说明验证结果及影响结论的重要未验证项，未经要求不为凑清单而堆砌额外防御代码或形式主义测试。
4. **高后果改动独立审查**：对资金/支付、鉴权/权限、不可逆数据迁移或删除、并发控制、对外 API 契约、核心状态机等高后果或难回滚改动（项目 `AGENTS.md` 可补充具体模块；无论改动行数多少），在授权和可用条件允许时，由另一个模型或干净上下文的子代理做独立审查；机械生成的改动重点审查生成规则并按风险抽查结果；无法安排独立审查时如实说明限制。审查方优先基于原始需求、实际变更及必要的上下文代码与测试证据独立形成初判（先不看实现方总结与会话过程），重点核查三问（未发现问题时说明核查范围与局限，不硬凑问题）：
   1. 哪些关键假设最可能有误？证据是什么？
   2. 现有验证会漏掉哪些有代表性的真实错误？
   3. 哪些新增代码、配置或抽象缺少当前需求支持，可以直接删掉？
```
