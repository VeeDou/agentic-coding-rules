## 一、Round 2 双方互相采纳的关键拼图

1. **Claude Code 贡献并获合入的关键判据**：
   - **值与行为二分法**（回应 Codex 问题 1）：差异是值（URL、文案、阈值、模型名）放进数据；差异是行为（流式协议、状态流转）先并列写两份，到第三处才抽象。
   - **封堵“自编理由”漏洞**（回应 Codex 问题 2 & 4）：提前抽象或加配置/缓存/兜底的理由，必须指向**现在已存在的事物**（用户原话、已有稳定抽象、已发生缺陷、实测数据、已知外部约束）。“以后可能需要”或自行脑补的“隐含性能/可用性要求”不算理由——若认为有隐含要求，必须移入“替用户做的决定/假设”清单交用户确认。
   - **恢复原核心句与精简概念**：完整保留用户原有的“面向用户或 agent 的接口从一开始就接受多样输入……”，去掉标题中多余的“防认知投降”概念。

2. **Codex 贡献并获合入的严谨边界修正**：
   - **工作区变更全景核对**：不仅看 `git diff`，还要结合 `git status` 与新增未跟踪文件，区分本次变更与工作区原有改动；归因重点放在有实质设计意义的新增概念上，避免机械罗列每个普通局部小分支造成噪音。
   - **防“内部不可能值报错”引发反向防御代码**：明确为“内部调用相信调用方与既有契约，不写静默吞错的兜底分支，也不为‘不可能值’到处新增冗余运行时校验”。
   - **理清“只列不补”与“完成义务”**：完成当前需求所需的必要验证与修复应正常执行；报告重要未验证项后，未经要求不为消除未验证项而擅自堆砌额外防御代码或凑数测试。
   - **对抗评审的证据开放与实事求是**：评审方先不看实现方的总结与会话过程，但可按需读取必要的调用方、现有测试与运行证据；三问核查若未发现问题可据实说明核查范围与局限，不硬凑问题。

## 二、终版合龙条文（拟替换 `~/agent-config/AGENTS.md` 中“实现的分量”章节）

```markdown
## 实现的分量（防过度设计，也防特化硬编码）

**核心**：通用性做在原语层，特化放在数据层，中间不加抽象层；两者冲突时，选概念更少的方案（通用化应该让机制变少，而不是变多）。

**防过度与防特化判据**：
- **值与行为二分**：差异是值（地址、格式、文案、阈值、模型名），放进数据/配置；差异是行为（协议、状态流转），先并列写，出现第三次才抽象（Rule of Three）。不为某个具体样例、测试或某一种用户习惯写死特例分支。
- **接口宽进**：面向用户或 agent 的接口从一开始就接受多样输入；能交给模型判断的流程，不硬编码成固定步骤。
- **证据准入（防脑补理由）**：只做本次明确要求的事；顺手发现的问题列为建议，不擅自改。提前抽象或新增配置项、缓存、兼容垫片、兜底分支，理由必须指向**现在已存在的事物**（用户原话、已有稳定抽象、已发生缺陷、实测数据、已知外部约束）。“以后可能需要”或自行脑补的“隐含要求”不算理由；若认为存在隐含要求，须作为待确认假设向用户提出。
- **边界错误处理**：只在真实边界（用户输入、网络、外部 API、跨模块持久化、并发写入）做错误处理；内部调用相信调用方与既有契约，不写静默吞错的兜底分支，也不为“不可能值”到处新增冗余运行时校验。

**非琐碎改动（新建文件，新增对外接口、配置项或依赖，或跨模块修改）执行规程**：
1. **动手前（读代码与列假设）**：
   - 先读目标代码、必要的调用方和现有测试（无调用方或测试时据实说明）；未搜索项目已有实现前，不新建通用 helper、工具类或模块。
   - 按任务风险明确预期行为与验证方式。对影响结果的默认值、范围取舍或冲突需求优先级，列出替用户做的具体判断（有则如实列，无则不写；涉及高后果分歧或多到列不完时，先询问用户）。
2. **交付前（核对实际变更与复杂度剃刀）**：
   - 先给客观证据（实际运行的命令与关键输出），后给结论总结。
   - 核对实际工作区变更（结合 `git status`、diff 及新增未跟踪文件，区分本次改动与原有改动）：审视具有实质设计意义的新增文件、公开接口、类/函数、配置项、兼容逻辑、兜底分支和依赖，确认每一项都能对应当前需求或已存在的约束；无法说明必要性的直接删掉，或改为文字建议。
3. **验证与未验证范围（如实报告，不为凑数补代码）**：
   - 测试应针对真实需求、契约、业务不变量或已知风险，并能发现有意义的错误；不写改错核心逻辑也不会失败的形式主义测试。
   - 完成当前需求所需的必要验证与修复应正常执行；交付时如实说明本次验证证明了什么、哪些重要边界尚未验证。未经要求，不为消除“未验证项”而擅自堆砌额外防御代码或凑数测试。
4. **高后果改动独立对抗评审**：
   - 对资金/支付、鉴权/权限、不可逆数据迁移或删除、并发控制、对外 API 契约、核心状态机等高后果或难回滚改动（无论改动行数多少；由确定性工具生成并经验证的纯机械改动除外，改为检查生成规则），在用户授权或项目约定的协作范围内引入另一个模型或干净上下文的子代理做独立审查。
   - 审查方优先基于**原始需求、实际变更及必要的上下文代码与测试证据**独立形成初判（先不看实现方的总结与会话过程），重点核查三件事（若未发现问题可据实说明核查范围与局限，不硬凑问题）：
     1. 哪些关键假设最可能有误？证据是什么？
     2. 现有验证会漏掉哪些有代表性的真实错误？
     3. 哪些新增代码、配置或抽象缺少当前需求支持，可以直接删掉？
```
