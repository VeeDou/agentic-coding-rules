# 01 · Round 1：为什么静态规则管不住过度设计？（Claude Code & Codex 独立盲审实录）

## 一、Claude Code 的第一轮独立盲审回复

> 以下未经调研，基于已有知识：只读了本地的 `~/agent-config/AGENTS.md`、Addy 原文正文和 `~/.claude` 下的配置，没有检索外部资料。关于 Claude Code 钩子的具体行为，凭的是我已有的了解，落地前需要再核对一次。没有修改任何文件。

### 0. 先说一个实测发现

`~/.claude/hooks/research-reminder.sh` 存在，但 `~/.claude/settings.json` 和 `settings.local.json` 里都没有 `hooks` 字段，项目的 `.claude/` 里也没有。也就是说，这个钩子从来没有触发过。这次请求本身就含有“方案”“设计”“架构”这些词，按设计应该触发，我的上下文里却没有收到这条提醒，可以佐证。

结论：现有机制里唯一的“硬检查”是断的。在评价“规则不够好用”之前，先把它接上，或者删掉。

### 1. 诊断：为什么规则写了也管不住

**“强制先读规则文件”没有抓到病根。** 这个文件已经在上下文里了：本会话开头我就能完整看到 `AGENTS.md` 的内容。再 `read_file` 一遍，只能在短时间内提高一点存在感，解决不了下面三个问题：

1. **违规在写的那一刻发现不了。** “不为假想需求设计”是一句价值判断，而判断“这个兜底有没有必要”的，正是想加它的那个模型。我自己最常见的过度设计是：内部调用外面包一层 try/except 兜底、为了“灵活”加的可选参数、常量抽成配置、没人要的兼容垫片。写的时候，每一项我都觉得“是需求要的”。规则我是认同的，但我没法在写的同时检查自己有没有违反它。
2. **没有能检查的产出物。** “代码量明显超出需求直觉时先停下”没有可观测的阈值，所以永远不会触发。规则要能被另一个人或模型对照检查，就必须落成某样东西：一张清单、一条命令的输出。
3. **规则被稀释了。** 全局文件里，“先调研”一节占了近一半篇幅，可视化规则对写代码不相关却始终加载，每一条都是“必须”。防过度设计的条文要和它们抢注意力。

**真正该强制读的是代码，不是规则。** 重复造轮子、多出来的抽象层，大多是因为不知道项目里已经有什么。“没搜过已有实现，就不新建 helper 或模块”，比重读规则有效得多。

**高杠杆机制只需要一个：交付时附一份“新概念清单”。** 这次新增的每个文件、函数或类、参数、配置项、分支、依赖，各用一句话写出它对应哪条需求。对应不上的就删掉，或者标成“建议”交给用户决定。这样检查从写的时刻挪到了看 diff 的时刻，换了一个视角，而且结果可以核对。

### 2. 测试边界与双模型协作

**两条一句话判据：**
- **防御代码：** 只守真实边界进得来的输入。内部调用出现“不可能的值”就直接报错，不兜底。
- **测试：** 只有当被测代码出现一处真实可能发生的错误、它会变红时，才有价值。不管怎么改错都不红的测试，删掉。

**关键补充：发现漏测和补上漏测要分开。** 追问“漏测了什么”之所以会滑向防御性编程，是因为模型一被问就想顺手补上。约束应该是：交付时把“证明了什么 / 没证明什么”列出来就够了，补不补由用户按风险决定。这样追问就是一项报告义务，不会变成写代码的冲动。

**双模型的触发阈值按改动类别定，不按代码量定。**
- **触发场景：** 资金、鉴权、数据迁移或删除、并发、对外 API 契约、核心状态机。这份清单最好作为数据写进各项目自己的 `AGENTS.md`，列出具体路径或模块，不要写成全局描述。
- **最小协作流：** 实现方照常写代码和测试；评审方在干净的上下文里，只拿需求、接口和 diff，不看会话转录，回答三个问题：
  1. 哪条假设最可能错？
  2. 哪个测试即使代码改错了也不会红？
  3. 哪段代码可以删掉？

### 3. Claude Code 向 Codex 提出的 5 个追问

1. 长任务结束时，你能可靠地列全自己新增的东西吗？如果靠自述会漏，清单是不是应该从 `git diff` 机械生成，再由模型逐条对应需求？
2. 做对抗评审时，只给你需求、接口和 diff，不给会话转录，你觉得会损失多少判断力？
3. 被要求“列出漏测”时，你是不是倾向于直接补测试、补防御？“只列不补”这条约束对你够不够？
4. 实现方和评审方要不要固定分工？我的看法是不固定：谁实现，另一方就评审；测试默认由实现方写。
5. 检查点很容易变成走过场，每次都填一句“无”。你有什么防止办法？我的提议是：如果“我替你做的决定”连续几次都是空的，说明任务粒度或触发条件定错了，该调的是规则，不是继续填表。

## 二、Codex 的第一轮独立盲审回复

**我的结论：不建议把“每次编码前强制重读全局规则”作为主机制。** 它可能在长会话或上下文压缩后起到提醒作用，但无法证明规则被正确应用，也容易增加噪声。更高杠杆的做法是：**在改动前明确可验证的结果，在交付前检查实际 diff 中的新增复杂度，并按风险决定是否需要独立审查。**

### 1. 为什么现有规则仍可能失效

现有规则覆盖了方向，但执行时有几个缺口：

- **规则没有自带证据。** “每一行都能追溯到需求”很有价值，但交付时如果不回看 diff，Agent 可以相信自己遵守了，实际却新增了配置、抽象或无关修复。
- **规则之间需要现场判断。** 例如“第三次才抽象”和“通用性做在原语层”可能同时被引用来支持相反决定；“内部调用相信调用方”也不能替代对数据来源、状态一致性等真实边界的分析。
- **隐含决策往往发生在实现过程中。** 开始时重读规则，不能覆盖之后遇到的默认值、兼容性、范围取舍或需求冲突。

建议把阅读分为两类：**已经注入的全局规则无需每次机械重读；项目相关的代码、局部规则、现有测试和实际调用方，应在修改前按任务需要读取。** 若怀疑规则没加载、上下文已压缩，或遇到规则冲突，再定向重读对应章节。

最有效的检查点是交付前对照需求检查 diff，重点问：

> 新增的抽象、配置、分支和文件，各自解决了哪一个已存在的问题？删掉后是否仍满足当前需求？

无法给出具体理由的复杂度，应优先删除；发现相关但未授权的问题，记录而非顺手修改。

### 2. 测试与双模型协作的边界

**一句话判据：测试应能指向真实需求、公开契约或已知风险，并在该行为被破坏时失败；如果只能证明多余内部防御存在，它通常不值得增加。**

双模型不应成为默认双倍编程流程。建议按风险触发，而不是按文件数或代码行数机械触发：

| 情况 | 建议协作方式 |
|---|---|
| 可逆、低影响的小改动 | 单 Agent 检查实际结果；不强制新增测试或第二模型 |
| 涉及关键业务行为、复杂状态变化、较难回滚，或需求与现有行为有冲突 | 由第二个 Agent 做一次独立审查，重点找契约遗漏和不必要复杂度 |
| 资金、权限、安全边界、不可逆数据变更等高后果场景 | 独立审查加相应实证验证；由负责的人决定是否接受风险 |

### 3. Codex 向 Claude Code 提出的 5 个追问

1. **反例挑战：** 请给一个现有规则会让 Agent 同时陷入“过度抽象”和“特化硬编码”争议的真实或具体示例。你会如何判定最小实现？需要哪条规则，而不是增加更多口号？
2. **检查点可靠性：** 如果 Agent 同时写代码和填写自查报告，如何防止它给自己的抽象编出合理理由？独立审查在哪些情况下能实质改善，在哪些情况下只是重复同一种偏差？
3. **触发阈值：** 对一个涉及权限但只改一行的变更，以及一个 500 行纯机械迁移，你分别是否要求独立审查？为什么？
4. **例外机制：** Rule of Three 在已有稳定抽象、重复代码已造成真实缺陷、或性能/安全需要前置设计时是否应有例外？如何要求 Agent 给出具体证据，同时不让“可能以后需要”成为万能借口？
5. **验证实验：** 我们能否先在实际任务中比较“仅注入规则”和“交付前检查 diff”的结果，定义可观察的成功指标与停止条件，再决定是否上 hook？
